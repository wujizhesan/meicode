# MewCode Phase4 缓存评估

## T0 真机探针结论（2026-08-08）

**环境**：DeepSeek V4 Flash（`https://api.deepseek.com`）

### 缓存字段名（确认）

- `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`（usage 顶层）
- 兼容字段：`prompt_tokens_details.cached_tokens`（同样填充）

### 命中行为（关键发现）

| 测试 | 前缀长度 | 结果 |
|------|---------|------|
| 短前缀（96 tokens）| 3 次相同请求 | **全 miss**（hit=0）——不缓存 |
| 长前缀（1176 tokens）| 前缀相同 + 历史增长 | **命中**：请求 2 hit=1152 / miss=32；请求 3 hit=1152 / miss=24 |

**结论**：
1. DeepSeek 自动缓存有**最小前缀长度门槛**（约 1k tokens 级别；实测 96 不缓存、1152 命中）
2. 「相同前缀 + 增长历史」下命中生效（共享前缀部分全命中，仅增长部分 miss）
3. **对 MewCode 的意义**：真实 system prompt（七模块）+ 六工具描述 ≈ 1500-2000 tokens，稳定前缀恰好跨过缓存门槛——P4 的模块化稳定前缀设计在真实场景可命中

### 设计影响

- T3：解析 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` 两个字段（`prompt_tokens_details.cached_tokens` 作后备）
- 缓存命中率 = hit / (hit + miss)；短对话（<1k 前缀）命中率恒 0 属正常，不显示误导数据
- 后续「项目指令文件加载」章节会进一步加长前缀，命中收益更大

## 真机多轮验证（T7，2026-08-08）

**场景**：live_agent.ts（写文件+读回多步任务，3 轮自主循环）

| 轮次 | 请求 tokens | 缓存 hit | 缓存 miss |
|------|------------|---------|-----------|
| 1 | 1407 | 0 | 1407（首次无缓存） |
| 2 | 1598 | 0 | 1598（缓存建立延迟） |
| 3 | 1667 | **1536** | **131**（仅新增历史 miss） |

**汇总命中率：33%**（hit=1536 / miss=3136），第 3 轮起稳定前缀全部命中，后续轮次命中率将随前缀复用继续上升。

**结论**：模块化稳定前缀（~1400 tokens system prompt + 工具描述）成功跨过 DeepSeek 缓存门槛，缓存策略生效。设计验证完成。

### 对比说明

- 结构化前（P3 单块 prompt）：无缓存字段解析，命中情况不可见
- 结构化后（P4 模块化）：命中率可见且有效（第 3 轮起 ~92% 前缀命中）
- 响应速度影响：命中部分免重新计算，多轮长对话收益显著
